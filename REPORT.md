| Показатель | Значение |

## 2. Архитектура

Три контейнера ZooKeeper имеют одинаковый список `server.N`, разные `ZOO_MY_ID`,
собственные volumes `/data` и `/datalog` и клиентские порты хоста 2181-2183.
Два координатора используют один connect string и session timeout 10 секунд.

Узлы приложения:

- `/skill-pairs/election` — эфемерные последовательные узлы election recipe;
- `/skill-pairs/epoch` — монотонная эпоха лидерства;
- `/skill-pairs/checkpoint` — номер следующего work unit;
- `/skill-pairs/result` — указатель на актуальный результат;
- `/skill-pairs/publications/item-*` — история принятых публикаций.

## 3. Проверки ансамбля

Команда `make status` показывает одну роль `leader` и две `follower`.
`make quorum-test` автоматически останавливает одного follower: оставшиеся два
узла отвечают. После остановки второго узла единственный сервер перестаёт обслуживать
запросы. Скрипт возвращает оба узла и сохраняет вывод в `logs/quorum-test.txt`.

`make ephemeral-test` создаёт эфемерный узел из короткой сессии `zkCli`, закрывает
её и новым подключением получает `Node does not exist`. Вывод сохраняется в
`logs/ephemeral-test.txt`.

## 4. Failover без fencing

`make demo-unfenced` запускает две копии, находит лидера и посылает ему `SIGSTOP`.
После истечения session timeout ZooKeeper удаляет его election-znode, запасной
координатор получает лидерство, читает чекпоинт и завершает работу. Скрипт выводит
измеренное время от `SIGSTOP` до строки `became leader`.

После публикации запасного старый лидер получает `SIGCONT` и публикует тот же
результат повторно. В двух журналах присутствуют две строки `wrote result`.
Перед расчётом создаётся пустой `/skill-pairs/result` с версией 0. Публикация
запасного делает `setData` и получает версию 1, повторная публикация старого лидера
увеличивает версию до 2. Это прямо соответствует критерию «указатель с версией 2».

Фактический прогон `unfenced-20261027T105157Z`: начальный лидер —
`coordinator-a`, запасной — `coordinator-b`, измеренное время смены лидера —
**10,800 с**. Запасной продолжил с checkpoint 15/120. В итоге обе копии записали
одинаковые 22 286 пар и SHA-256
`ed6333305917179aa98d99c3040edb3673b8c6f97cbc597fce4dc97e58862a99`,
а указатель завершил работу с `dataVersion = 2`.

## 5. Failover с fencing по эпохе

`make demo-fenced` повторяет опыт с `FENCING=1`. Новый лидер атомарно увеличивает
эпоху. Получатель публикации сравнивает эпоху результата с текущей эпохой. После
`SIGCONT` старый лидер предъявляет устаревшую эпоху и получает в журнале
`BadVersionError stale result rejected`. В истории остаётся одна публикация, а
указатель принадлежит запасному координатору. `make verify` проверяет эти условия.

Фактический прогон `fenced-20261027T105312Z`: начальный лидер —
`coordinator-a`, запасной — `coordinator-b`, время смены лидера — **10,338 с**.
Запасной продолжил с checkpoint 15/120, записал 22 286 пар с тем же SHA-256;
просроченная запись `coordinator-b` отклонена при `result_epoch=1` и
`current_epoch=2`. Указатель остался от запасного и имеет `dataVersion = 1`.

## 6. Ответы на вопросы

### Почему серверов три, а не два и не четыре?

ZooKeeper принимает запись только при наличии большинства. Для трёх серверов
кворум равен двум, поэтому отказ одного сервера допустим. Для двух кворум тоже равен
двум: отказ любого узла останавливает записи, то есть дополнительный сервер не даёт
отказоустойчивости. Для четырёх кворум равен трём и также допускается отказ только
одного сервера, как у трёх, но добавляются стоимость, сетевой обмен и ещё один узел.
Чтобы пережить два отказа, нужен ансамбль из пяти серверов с кворумом три.

### Почему fencing проверяет получатель записи, а не ZooKeeper?

ZooKeeper знает, кто владеет сессией и какова версия znode, но не знает смысла
внешней операции — записи файла, объекта S3 или строки БД. При сетевой паузе старый
лидер может не узнать, что его сессия истекла, и продолжить уже начатую работу.
Поэтому монотонную эпоху нужно передавать вместе с каждой записью, а система,
которая реально меняет данные, обязана отвергать эпоху меньше последней принятой.
Проверка только на стороне координатора ненадёжна: именно зависший координатор и
может ошибочно считать себя лидером. ZooKeeper выдаёт упорядоченный fencing token,
но обеспечить его применение к внешнему ресурсу способен только получатель записи.

## 7. Команды воспроизведения

```bash
cp .env.example .env
make build ensemble
make status
make quorum-test
make ephemeral-test
make demo-unfenced
make demo-fenced
make verify
```

Для GitHub следует добавить содержимое проекта, журналы из `logs/` и, при желании,
скриншоты терминала. Секретов в `.env` нет, но файл исключён для единообразия.
